# 確認モードと、呼び出し番号表示の参照アプリ

構想は[#157](https://github.com/Suisan-neki/execution-evidence-lab/issues/157)、今回の実装範囲は[#159](https://github.com/Suisan-neki/execution-evidence-lab/issues/159)。AIなどを使って作った人が、仕組み・実際の結果・未確認事項を同じ根拠から確認するための試作。

## 確認モードを使う

```bash
cargo run -- app data/app
```

表示されたURLを開く。「確認モードと確認資料」で汎用／医療を選び、記入者と理由を入力して記録する。構成図の画面にも同じ操作がある。

モードの選択は事例へ保存する。「説明の詳しさ」はこの欄と確認候補の説明を切り替え、ブラウザだけに保存する。条件・根拠・判定は変更しない。医療モードを選んでも権限や通信の制限は設定されない。

確認候補は最初から事例に混ぜない。利用者が候補を選ぶと、未採用の提案という出所を付けてmanual_onlyの条件を追加する。観測方法を設定して試験へつなぐまでは判定できない。候補を追加しただけで担当者の回答や業務上の要件を得たとは扱わない。汎用へ戻しても追加済みの条件を削除しない。

## 参照アプリで一往復する

Rust・Git・Node.js・Python 3が必要。この手順は同梱する信頼できる参照コードをlocal方式で実行する。localはOSによる隔離ではない。実患者の情報や信頼できないコードを使わない。

```bash
cargo build --locked
npm run demo:queue -- evaluations/queue-reference
cargo run -- review evaluations/queue-reference/case --port 8765
```

保存先は新規のディレクトリにする。再実行時は別の保存先を指定する。既存の記録を上書きしない。

`http://127.0.0.1:8765/architecture`では番号表示の全体図・内部構成と観測を確認する。要素・接続から疑問と個別の試験結果を開き、根拠から元の図へ戻れる。旧版と修正版は同じ構成の配置を使うが、コードの参照と試験結果は各版の記録を使う。描く構成や表示文が変わった場合は古い図を使わず、構成一覧で確認する。

この手順では次を行う。

1. 参照コードのコピーから合成のGitリポジトリを作る。表示番号に1を足す誤りを入れた版を固定する。
2. 実際に読んだ固定版ファイルをRustの静的解析へ渡す。構成モデルと「保存した番号と表示した番号の違いに気づけるか」という合成の疑問を記録する。
3. 架空の番号42をHTTPで送る。保存物には試験識別子を付け、表示番号・保存物・別プロセスの読出し・再起動を別々に確認する。
4. 保存は成功しているが表示が異なる結果を残す。改修の判断を記録して表示を修正し、新しいコミットへ参照を更新する。
5. 旧結果が再確認待ちになることを確認し、正常試験・保存先の異常・保存物の観測欠落・正常な再試験を実施する。
6. 汎用へモードを変更しても過去の結果が変わらないことを確認する。医療向けに追加した手動確認の候補は未確認のまま残す。
7. 同じ事例版から確認資料を作る。原文ログを入れていないことも照合する。

| 試行 | 保存物の観測 | HTTP表示・再起動 | 条件全体の判定 |
| --- | --- | --- | --- |
| 表示を誤る旧版 | 試験識別子を確認 | 入力42に対して43を返す | 条件を満たさない |
| 修正版・通常時 | 試験識別子を確認 | 42を返す | 条件を満たす |
| 保存先と同名のディレクトリ | 保存できない | 保存失敗を返す | 条件を満たさない |
| 保存物の読み出しを止める | 未観測 | 42を返す | 判定できない |
| 正常な再試験 | 試験識別子を確認 | 42を返す | 条件を満たす |

HTTPの表示内容は対象内の試験クライアントが照合した報告。基盤による保存物の直接読取や、別プロセスによる読出しと区別する。ブラウザ描画は別の操作試験で確認する。ネットワーク全体や医療業務での利用可否を確認した結果ではない。

`evaluations/queue-reference`には`understanding.json`・`result.json`・`review.json`・`review.html`と事例・固定版のリポジトリを保存する。`example/queue-display`は合成のリポジトリ名で、実在する公開リポジトリへのリンクではない。対象コードは同じ保存先の`repo`でコミットを照合する。

## 確認資料を作る

画面で「他の人と確認する資料」を開き、現在の結果を確認する。内容を確認してJSONまたはHTMLを保存する。HTMLの保存前に事例が更新されていた場合は読み直しを求める。

```bash
cargo run -- case report evaluations/queue-reference/case --output evaluations/queue-review.json
cargo run -- case report evaluations/queue-reference/case --output evaluations/queue-review.html --format html
```

CLIも既存の出力先を置き換えない。HTMLは追加のサーバーや外部アセットなしで読める。条件、判定と根拠、再確認の理由、構成、質問、人の判断を残す。詳しい情報は同じ資料内で開ける。

原文ログ・実行入力・認証情報・画面写真は埋め込まない。試験結果の要約からも標準出力・保存物の抜粋・実行コマンドを除く。ただし条件文や構成の説明、質問や判断理由に利用者が記入した情報は含む。自動的な匿名化や機密情報の検出は行わない。共有前に内容と相手を確認する。

## 形式と履歴

モードの選択は`profile_history`に選択版・カタログ版・記録した事例版を追加する。取り込んだ根拠には当時の`review_profile`を残す。過去の選択や根拠は書き換えない。判定規則を変更すると既存の条件版管理に従って再確認が必要になる。

旧形式1は引き続き読める。モードを記録すると事例を形式2へ移行する。旧バイナリが新しい履歴を無視して更新しないようにした。形式2を使った事例は、この変更を含むバイナリで読み書きする。全版バックアップは形式1から2への移行を含めて復元できる。

## 今回確かめていないこと

実参加者の理解と判断、医療機関の実際の業務条件、医療上の妥当性、本番環境の権限と運用は未確認。OpenEMR・OHIF・MONAIの目標を引き継ぎ、この参照アプリの完成だけで研究や汎用版全体の完成にはしない。


## 構成図の配置と根拠を分ける（#161）

図の配置はコードのコミットとは別に照合する。Rustが要素の識別子・階層・種類・表示名・説明、接続の識別子・両端・表示名・説明、環境・固定イメージ・ブラウザ版を組み込み構成と比較する。すべて一致した場合だけ同じ配置を使う。構成モデルの版とコードのコミット、疑問と試行の参照を置き換えることはしない。

これは固定した4件の構成に対する表示の対応。任意のコードから構成を自動抽出する機能や、任意の構成の図を実行時に生成する機能は未実装。
