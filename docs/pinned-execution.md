# 固定版の外部コードと観測をつなぐ

2026-10-13の追加実装。PR #126。Node.jsとPythonの起動ファイルを、Gitの固定コミットからコピーして実行する。対象アプリが報告した観測を条件へ対応づけ、結果からコード・観測・改修前後の記録へ戻る。

## 再現する

```bash
git fetch origin
git switch main
git pull --ff-only
cargo build --locked
npm run test:external
```

合成のGitリポジトリで、保存物との比較条件を誤った旧版を試す。改修判断を残し、比較条件を直してコミットする。参照先を更新すると古い結果が再確認待ちになり、新しい版を同じ入力で実行すると成功の観測になる。正常・人工失敗・観測欠落・食い違いも再現する。

出力先は`evaluations/pinned-.../`。`result.json`に前後のコミット・判定・比較がある。`case/`は通常のレビュー画面で開ける。

```bash
cargo run -- review evaluations/pinned-.../case
```

この例のoriginは合成の`example/observable-store`で、実在する公開リポジトリを調査した結果ではない。コードへの復帰を試す際のブラウザ試験は、その固定した応答を別に用意する。

## 自分の対象で進める

1. 公開GitHubを理解画面で読み、コード参照を持つ確認事項を作る。未定義の条件はUnknownで始まる。
2. テスト画面の「このコードの試験を設定する」を開く。条件に対応する観測名・対象を入力し、記入者と理由を付けて保存する。
3. Node.jsかPython、起動ファイル、引数、入力、待機上限を指定する。設定を保存してCLIから実行するか、以下の実行モードで画面から実行する。
4. 観測形式に対応した対象コードのローカルGitリポジトリを用意する。`repo prepare`で、試験設定に指定した公開GitHubの固定コミットを新しいディレクトリへ取得できる。originと、画面から引き継いだ固定コミットが一致する必要がある。
5. CLIまたは画面で実行する。実行中に条件が変わった場合は試行を残し、取り込みを拒否する。
6. 画面で最新版を読み直し、条件の結果・観測の根拠・起動ファイル・固定版・ランタイムを確認する。
7. 改修後は理解画面で別の版と比較し、参照先を更新して新しい試行を行う。旧試行と判断当時の根拠は書き換えない。

```bash
# 公開GitHubから新規に取得する場合。既存ディレクトリは置き換えない。
cargo run -- repo prepare NEW_REPOSITORY_DIR RECIPE_JSON
cargo run -- case execute CASE_DIR RECIPE_JSON --repository-root LOCAL_REPOSITORY --mode local --actor 記入者 --reason 試験理由
```

`repo prepare`はGitのオブジェクトだけを取得し、checkoutや対象コードの実行はしない。認証なしで取得できない場合は失敗する。途中で失敗したディレクトリは成功した取得として扱わず、`prepared.json`は完成時だけ保存する。取得は浅い履歴で対象コミットのオブジェクトをまとめて取得する。コピーのサイズ上限とGit取得時の転送量の上限は別で、転送量そのものの制限は未実装。実行時に固定コミットからコピーするため、取得用ディレクトリにアプリの作業ファイルは展開しない。

localは、読み取ったGit blobをコピーし、環境変数を引き継がず、試行用のworkでコードを動かす方式。OSによる隔離ではなく、自分で確認したコードに使う。未コミットの作業ファイルはコピーしない。symlink・submodule・特殊ファイルがあれば起動を拒否する。

Linuxのbubblewrapを使用する場合は`--mode bubblewrap`へ変える。namespaceを分離し、固定版を読み取り専用で共有する。外部ネットワークを共有せず、書き込み先は試行のworkと一時領域にする。利用できない場合はローカルへ自動で切り替えない。起動されたという申告と、実行が成功したことを区別する。

現在は任意のアプリを自動で起動・計測する機能ではない。依存パッケージのインストール、Rust等のビルド、iOS・AWS環境の再現も別途必要。対象アプリに観測を追加する手順を次に示す。

## 画面から固定版を実行する

サーバー起動時に、確認した対象コードのGitリポジトリと実行方式を指定する。

```bash
cargo run -- review CASE_DIR --repository-root LOCAL_REPOSITORY --execution-mode local
# 利用できるLinux環境で隔離方式を要求する場合
cargo run -- review CASE_DIR --repository-root LOCAL_REPOSITORY --execution-mode bubblewrap
```

画面の「このコードの試験を設定する」で起動設定と入力を確認し、記入者と理由を入れて「この固定版で試験を実行する」を押す。固定コミットは確認事項のコード参照を使い、未コミットの作業ファイルは実行しない。起動時に指定したリポジトリ以外のパス・方式・任意コマンドを画面から指定する操作はない。設定の保存とCLI実行も引き続き使える。

一件を別スレッドで実行し、実行中も条件や根拠を読める。二重起動は拒否する。受付、実行中、結果の取り込み完了、実行または取り込み失敗を表示する。「取り込み完了」は条件を満たすという意味ではなく、各条件の判定と観測の根拠を確認する必要がある。画面を開き直しても、サーバーが動いていれば進行中の試験を確認できる。

古い事例の版からの起動は拒否する。実行中に事例が変わると、現在の事例は上書きせず試行記録を残す。画面には取り込みできなかった理由と試行ディレクトリを表示し、最新版で再試験できる。取り込み完了の状態を読んでから事例を読むため、取り込み前の事例を完了した結果と混同しない。

通常の `review CASE_DIR` は外部実行を有効にしない。実行モードはサーバー単位で一つのリポジトリ・一件の試験に限定し、別サーバーやCLIからの実行を全体で排他する仕組みはない。画面の中断ボタン、サーバー再起動後のジョブ管理、Git読み出し・コピーを含む全工程の待機上限は未対応。指定した待機上限は対象プロセスに適用する。localの隔離・子孫プロセス・外部状態の制限は以下の説明を参照する。

## 過去の設定から再試験を準備する

実行記録がある条件では、試験設定の中で過去の試行を選び、「過去の設定を入力欄へ読み込む」を押す。言語・起動ファイル・引数・入力・待機上限を入力欄へ戻せる。同じ条件とリポジトリに対応する外部試行だけが候補になる。

新しく保存する試験設定は、現在の条件に対応づけたコード版と観測名・対象を使う。読み込んだ旧試行の版、現在の版、観測条件の変更を画面に表示する。入力と起動設定が新版にも使えるか確認してから保存する。旧試行のコード版や観測規則を自動で現在の条件へ戻す操作ではない。

読み込みと試験設定の保存は、入力欄とダウンロードだけを扱う。保存済みの試行・判断・現在の判定は変えない。実行と新しい結果の取り込みは、CLIまたは実行モードで開いた画面で行う。最新版を読み直しても、編集中の入力と読み込んだ試行の表示を保持する。画面全体を開き直した場合は、過去の試行を選び直す。

## 対象コードへ観測を追加する

共通の環境変数は次のとおり。

| 変数 | 意味 |
| --- | --- |
| EEL_RUN_ID / EEL_RECORD_ID / EEL_ATTEMPT_ID | 試行・データ・試行内の送信を区別する識別子 |
| EEL_INPUT | 試験設定に指定したJSON入力のファイル |
| EEL_WORK_DIR | 試行ごとの新しい作業領域 |
| EEL_OBSERVATIONS | 構造化した観測を出力するJSONLファイル |
| EEL_SOURCE_ROOT | コピーした固定版のルート |

Node.jsのES Modulesでは、`adapters/observation/observe.mjs`を対象側へ追加して使う。パスは対象の配置に合わせる。

```javascript
import { createObserver } from './observe.mjs';
const observe = createObserver();
// 状態を実際に確認した結果を渡す。成功を固定値として作らない。
observe('stored_matches_input', 'record-1', matches ? 'pass' : 'fail', '保存物を読み出して入力と照合した');
```

Pythonは`adapters/observation/observe.py`の`Observer`を使う。

```python
from observe import Observer
observer = Observer()
observer.emit('stored_matches_input', 'record-1', 'pass' if matches else 'fail', '保存物を読み出して入力と照合した')
```

どちらも順序番号・試行識別子・呼び出し元のパスと行を付ける。場所は対象プロセスが申告したもので、独立した実行トレースではない。一つのプロセスで一つの観測器を使う。複数プロセスのJSONL同時書き込みと順序統合は未対応。Node.jsはES Modulesのスタック表現に対応し、変換後のコードやsource mapの照合は未実装。

## 判定と照合

条件へ対応づけた観測名・対象を、同じ試行識別子の中で探す。試行が正常に終了し、終了時の固定版の内容とファイル一覧が一致し、観測の整合性を確認できた範囲で判定する。

| 観測 | 判定 |
| --- | --- |
| 対応する成功だけがある | 条件を満たす（選んだ観測の範囲） |
| 対応する明示的な失敗だけがある | 条件を満たさない |
| 成功と失敗が食い違う | 判定できない |
| 対応する記録がない・ファイルがない | 判定できない |
| 別試行、欠番、不正な行、壊れたJSON | 記録を採用せず判定できない |
| 待機上限・出力上限・終了失敗・固定版の変化 | 判定できない |

終了コード0、保存物があること、別の試行の成功を、欠けた観測の代わりにしない。条件の版・文・出所・コード参照・観測規則が現在と一致しない試行は取り込まない。入力・引数・ランタイム・方式を条件ごとの依存先に保存し、別の条件の設定を取り違えない。

観測名・対象と業務条件の対応は人が設定する。対象コードの報告が条件の意味を十分に確かめるか、独立した状態やログと一致するか、別途確認する必要がある。医療機関の採用済み要件や独自性を、この実装だけから確定しない。

## 記録と制限

試行には固定版の`source/`、新しい`work/`、`recipe.json`、`execution.json`、`observations.jsonl`、stdout/stderr、従来のmanifest・events・assessment・report・completeを残す。事例へは実行対象・観測・出力の先頭8KiBを複製する。実行対象のoriginは宣言された出所で、GitHubから取得したことや真正性を保証する署名ではない。

固定版は512ファイル、各4MiB、合計32MiB。入力は128KiB、試験設定全体は192KiB、観測は1MiB・2000件、待機上限は最大300秒。stdout/stderrの1MiB超過は監視して停止するが、監視の間に超過分が書き込まれる可能性がある。CPU・メモリ・ディスク全体の上限をOSで設定する処理は未実装。

localの終了時の照合は、実行中にコードを書き換えて戻す操作を検出する保証ではない。タイムアウトでは直接起動したプロセスを停止・回収する。local方式の子孫プロセス全体の停止・外部状態の復元・未信頼コードの安全性は保証しない。固定版のコピーと隔離・可逆性の評価を同じものとして扱わない。

現在の合成例は、実AWS・App Store提出版・iOS・管理画面を照合した結果ではない。本人の理解・仕様採用・参加者評価・研究手法の優位性は別に確認する。
