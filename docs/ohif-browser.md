# OHIFの一覧と画像を分けて試す

OHIF Viewerの固定コミットをビルドし、試験専用のOrthancから合成DICOMを取得する。検査一覧の表示・取得、画像の取得、canvasの明暗、画像サーバーの直接読取を、別の観測として残す。画像要求だけをHTTP 503で拒否する構成と、復旧後の構成でも試行する。

## 実行する

新しい作業コピーで、DockerとNode 24.19.0を用意する。依存導入とビルドの設定は[固定した環境の手順](pinned-environments.md)を参照。

```bash
cargo build --locked
npm ci --ignore-scripts
npx playwright install --with-deps chromium
node tools/environment-smoke.mjs ohif-build
node tools/ohif-smoke.mjs
cargo run -- review evaluations/ci-ohif/case
```

最初のコマンド群はOHIFの依存導入とビルド、固定ファイルを改変した準備失敗を確認する。続く`ohif-smoke`は、正常・画像要求の拒否・復旧後の再試験を同じ事例に残す。既存の出力を上書きしないため、出力先がある作業コピーでは再実行できない。

試行に使ったレシピは`evaluations/ci-ohif/*-recipe.json`、事例と実行記録は`evaluations/ci-ohif/case/`へ保存する。正常時と拒否時の部分観測は同じ条件で比較できる。画面写真も各試行に残る。CIはJSON・画面写真・ログを7日間保管し、ビルドした静的ファイル全体は保管しない。再現時には固定設定からビルドする。

## 固定した対象と生成物

OHIFのコミットとビルド環境は`examples/ohif-build/recipe.json`を使う。Webサーバーはnginx 1.27.4、画像サーバーはOrthanc 26.9.1のダイジェストを固定する。ブラウザーは基盤のPlaywright 1.62.1が指定するChromiumを使う。描画にはSwiftShaderを明示し、起動引数もブラウザーの記録へ残す。実行時のブラウザーの版が違えば試行しない。

`Service.web_build`には、ビルドの試行ID、生成物の一覧のSHA-256、ソースの固定コミットを指定する。基盤の起動環境に`EEL_PREPARED_ENVIRONMENTS`で準備結果の親ディレクトリを指定する。レシピからホスト上の任意のディレクトリを指定することはできない。

基盤は準備の成功、ソース、導入一覧、生成物の名前・大きさ・SHA-256を確認する。リンク、パスの脱出、重複、上限超過は拒否する。一覧にあるバイト列だけを一度コピーし、それをnginxのコンテナへ渡す。元の生成物が後で変わっても、試行に渡す内容は変わらない。ビルド環境のイメージ・基盤スクリプト・導入一覧・生成物の一覧のハッシュを、試行の構成要素にも残す。

試験用のOHIF設定、nginx設定、合成データを作る設定はレシピに明記する。設定ファイルの上書きはコンテナの中で行い、ビルド時の生成物と区別する。

## 合成データと操作

`examples/ohif-browser/fixture.mjs`は、64×64画素の明暗を持つDICOMを生成する。画素値は0〜4095の順序付きの値で、実在の患者や撮影画像は含まない。検査UID、シリーズUID、画像UIDと画素のSHA-256をレシピに残す。

準備用ページからOrthancへ合成DICOMを登録し、登録が終わってから試験操作を始める。準備中の通信は試験操作中のHTTP観測に混ぜない。その後、OHIFの検査一覧を開き、合成患者名の表示を読み、同じ検査UIDのビューアーを開く。

| 観測 | 根拠 | 判定しないこと |
| --- | --- | --- |
| 一覧の表示 | OHIFの表から読み出した文字列 | 画像の取得や描画 |
| 一覧の取得とUID | ブラウザーが受け取ったQIDOの状態コード・本文 | 画像データの取得 |
| 画像の取得 | 画像要求の状態コードと、multipartから読み出した画素のSHA-256 | 画像の向きや診断上の正しさ |
| canvasの明暗 | canvas領域の画面写真を基盤側でPNGとして読み出した画素 | 全画素の再構成や臨床上の妥当性 |
| サーバーの画像 | 基盤からOrthancへ直接GETした画素のSHA-256 | ブラウザーの通信や描画の成功 |

canvasは64段階以上の明暗と4,096画素以上の黒以外の画素があることを確認する。この数値は合成画像の試験用に選んだもの。要素の存在や大きさだけで描画成功にはしない。canvasを読み出せなければ未観測とし、読み出せた画素が指定した明暗の条件を満たさなければ、その条件の失敗とする。

画面写真のRGBAのハッシュ、DICOMwebの画素データのハッシュ、ビルドしたファイルのハッシュは、それぞれ別のバイト列を対象にする。これらのハッシュが互いに一致するとは扱わない。DICOMwebの画素だけを、合成データを作ったときの画素のハッシュと照合する。

## 画像要求を拒否する

拒否する構成では、nginxの試験用設定で`/frames/`を含む画像要求だけをHTTP 503にする。検査一覧やメタデータの要求はOrthancへ通す。サーバー全体の停止や、保存画像の破損を再現するものではない。

`http_rejected`の試行では、拒否を確認する観測IDと状態コードを指定する。基盤は、宣言した試験操作に対応するHTTP応答が実際にそのコードになった場合に、故障を確認できたと記録する。対応する要求がなかった場合、応答が相反した場合、記録上限に達した場合は、故障を確認できたとしない。

一覧が表示でき、ブラウザーの画像要求は拒否され、Orthancからの直接読取では画像がある、という状態を別々に残す。拒否の解除後は新しい試行を作る。過去の失敗や未観測を、新しい成功で書き換えない。

## 確認範囲と読む順番

合成画面では、明暗のあるcanvasと空のcanvas、画像の応答本文のハッシュ、観測がないときの扱いを確認する。生成物の改変・リンク・異なるソース・準備失敗を拒否するRustのテストも実行する。この開発環境にはDockerがないため、実際のOHIFとOrthancの確認は`Pinned target environments`のCIで行い、成否と実行記録をPRに残す。

読む順番は`tools/ohif-smoke.mjs`、`src/prepared_web.rs`、`src/container.rs`、`src/browser.rs`、`tools/browser-runner.mjs`、`src/http_probe.rs`、`src/trial.rs`。操作と根拠の対応を確認してから、生成物の検査、HTTPと画素の観測、条件ごとの判定を追う。

構成図へのOHIF固有の図の追加、実参加者との評価、医療業務で必要な画像の正しさは、この試行では確認しない。試験専用の合成データと一つの画像で、部分観測と失敗・再試験の記録を確かめる段階である。
