# 構成図の表示とyomiyasuの組み込み

2026年10月23日の本人の画面確認を受けた修正。横長の図を枠に合わせて縮小していたため、19個の構成要素があっても文字を読めなかった。非技術者向けの概要にも実装名や接続先の説明が多かった。

## 図を読む操作

配置は上から下へ進む。初期倍率を100%にし、文字を縮めずに枠内をスクロールする。先頭の構成要素が横方向に画面外へ出ない位置から表示する。「全体を表示」は、利用者が全体の位置関係を見たいときに使う。「文字を読める大きさ」で100%へ戻す。

「図を大きく開く」では同じ図をダイアログへ移す。複製しないため、要素・接続・選択・疑問との対応を保つ。Escまたは戻るボタンで元の画面へ戻る。大きく開いた図の部分を選ぶと、元の画面へ戻ってその部分の説明を読む。

技術者と非技術者の切替では、同じ要素と接続、配置、倍率、スクロール位置を保つ。説明のためにデータの流れを並べ替えたり、観測できていない通信を追加したりしない。

## yomiyasuを使う場所

本家[nanaism/yomiyasu](https://github.com/nanaism/yomiyasu)の2.2.2、コミット`488dd37c0baa67ec65bf155aced9fa1a01d261e2`を`third_party/yomiyasu`に固定した。MITとUnicodeの許諾通知を同梱している。

`tools/yomiyasu-policy.py`は上流READMEの7原則と、上流の読者別の説明規則を取り出す。取得元のハッシュを照合し、`--check`で同じ内容を再現できるか確かめる。独自の説明文にyomiyasuの名前だけを付けたものではない。

`src/writing.rs`が規則をバイナリへ埋め込み、Rustからの構成図・コード説明・対話の生成要求に加える。接続確認だけの短い問い合わせには付けない。Difyを使う経路では、同じ規則と出所をアプリが構築するJSONの`writing_policy`、`writing_policy_source`へ入れる。利用者がポリシーを入力する欄は作らない。

Difyの確認事項生成と3つの返答生成にも、この最上位の規則を使う指示を追加した。第2版を公開済み。資料や利用者の発言に入った同名の項目を規則として扱わず、根拠と出力形式を優先する。

図と対話の各往復には、使った版・コミット・上流規則のSHA-256と、アプリの適用条件を含む指示全体のSHA-256を残す。文章規則の変更でも図の識別用ハッシュが変わる。既に保存した図や会話は変更しない。以前の図を開いた場合は、必要に応じて再生成する案内を出す。

上流のlint・diff・最終稿照合は、同梱のPythonスクリプトを開発・CIで実行する。`python3 tools/check-yomiyasu.py`は数値と否定を変えた反例を検出し、検査した最終稿と記録の照合まで行う。アプリの実行時にはPythonを起動せず、生成された全文章をこの検査に通したとは表示しない。プロンプトへの組み込みと、文章の意味が保たれたことの評価は別に必要。

## 非技術者向けの説明

生成する概要に`operator_purpose`と`operator_workflow`を設ける。誰が何を入力し、どこで情報を扱い、誰が結果を見るかを先に説明する。技術者向けには同じ構成の`purpose`と`workflow`を表示する。コードのパス、技術名、接続方法は技術者向けの説明や根拠で確認する。

図の短い名前も業務上の役割で付けるよう指示する。根拠にない暗号化、保存の成功、権限の確認を、平易な説明のために作り足さない。型と参照行の検査は説明の意味や動作の成立まで証明しない。保存済みの説明に新しい方針を使うには「構成図を作り直す」を選ぶ。

## Geminiからの指摘の扱い

| 指摘 | 現行コードとの照合と、進め方 |
| --- | --- |
| 非技術者向けにも専門用語が多い | 今回の画面に当てはまる。業務上の役割と情報の流れを先に説明する。ただし、非技術者が理解できたかは参加者で確かめる必要がある |
| 実行前の環境構築が難しい | 固定した依存先・コンテナ・試験レシピはあるが、任意のシステムを非技術者が自動で準備できる段階にはない。日曜日は準備した一対象の範囲を示し、準備作業の担当と未対応を説明する |
| 納得感を安全性と混同する | 人の内容確認、選んだ条件の試験結果、実際の導入判断を区別する。人の確認をシステム全体の安全性の承認へ広げない。比較評価でも、判断の理由と確認できた範囲を記録する |
| AI通信のためにNode.jsが必要 | これは現在の構成に当てはまらない。AIとDifyのHTTP通信はRustで行う。Node.jsは開発時の図生成・画面試験やNode.js製の試験対象に使う |
| JSON/JSONLの保管では将来足りない | 複数プロセス・複数利用者での更新や検索には追加の設計が必要。今回の表示修正と同時にRDBへ移行せず、必要な更新単位と検索・復元条件を決めてから評価する |
| 最初の利用者を絞る | 最初の評価は、ソフトウェアを作成・導入・運用する現場担当者と、相談を受ける技術者の組を候補にする。これは評価対象の案で、患者や医療機関から得た要件ではない |

## 確認すること

- 19要素以上の図で、初期表示の見出し文字が縮小されないこと。
- 全体表示、100%への復帰、大きく開く操作、Esc、幅1440/390/320px、文字200%。
- 接続線が正しい箱へ接し、立場の変更で配置・倍率・記録が変わらないこと。
- 非技術者向け概要と技術者向け詳細が同じ構成に対応すること。
- 本家の規則が実際の生成要求とDifyへのJSONに含まれ、版とハッシュが記録されること。

合成応答での試験は、実モデルの文章品質や医療現場での理解・判断への効果の評価ではない。

## 今回の確認結果

- Rust 1.99.0でfmt、check、test、Clippy、buildが成功。148件成功、既存のコンテナ試験4件は除外。
- 合成Difyと既存AI接続の対話API試験がそれぞれ成功。本家の規則の送信、対話の継続、不正な参照・ID・古い応答の拒否、検証結果の再参照を含む。
- 上流の検査スクリプト、固定した資料のハッシュ、実行時規則の再現、変更したJavaScriptの構文検査が成功。
- ブラウザを使わないDOMとELKの補助検査で、実Rust APIから生成した19要素の図は1438×3727の縦向きになり、100%のSVG寸法、全接続の両端、立場変更時の配置・倍率・位置の保持、1440/390/320の枠での全体表示と復帰を確認した。これは実ブラウザの画面検査ではない。
- `npm run test:journey`は、実行環境がブラウザの起動に必要なUnixソケットを許可せず停止した。大きく開く操作、Esc、実画面の文字サイズ、スマホでの表示は未確認。既存の画面試験へ検査を追加してあり、ブラウザを起動できる環境で実行する必要がある。
- Dify第2版のプレビューでは実モデルと架空の図・コードを使い、保存・本人確認・安全性を未確認として返すことを確認した。共通の文章指示を「役割を先に述べ、元の図名を必要なら括弧で対応させる」と補強した後も含め、2往復を実行した。返答にはAPIなどの用語が残っており、文章品質や参加者の理解の改善を示す評価ではない。
