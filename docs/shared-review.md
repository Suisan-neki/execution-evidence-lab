# 条件と根拠の共同レビュー

2026-10-07の試作。親#121、実装PR #110。共有した認識が正しいか、根拠に応じた安心感が生まれるかは別に評価する。

## 一件を進める

READMEの`case init`と`review`で始める。初期事例は合成入力を使う練習用で、実際のCASE-001ではない。

1. 記入者・立場・今回の理由を入力する。立場は自己申告。
2. 期待する動作を確認事項として記録する。認識・発言、コード上の事実、提案、未回答は種類と出所を付け、関連する条件を指定する。
3. 誰が・どの記録を・いつ見る必要があるかを回答する。未回答があれば条件はUnknown。回答しても未定義の判定方法を成功へ変えない。
4. 保存のデモを試す。判定理由から根拠の行を開き、実行条件と観測できない範囲を見る。
5. 質問、追加確認、改修、保留、公開・導入の判断と理由を保存する。改修へのIssue・PR参照を付けられる。ここから実際の公開は実行しない。
6. 条件、コード等の現在の宣言を更新する。古い結果が使えない理由を確認し、新しい試行を行う。判断当時の根拠は履歴に残る。
7. 比較資料を新しい出力先へ書き出す。回答欄は未記入で、実参加者の評価として数えない。

## 記録と版

| 記録 | 内容 |
| --- | --- |
| statements | 種類、立場、内容、出所、関連する確認事項 |
| checks | 条件文、出所、版、判定規則、依存先、質問と回答の出所 |
| context | 現在のコード・入力・環境等の宣言値 |
| evidence | 取り込み時の条件版、実行条件、依存先の値と出所、観測記録のコピー |
| decisions | 立場、記入者、理由、行動、改修参照、判断時の条件と根拠。安心感と時間は任意入力 |
| history | 誰が・なぜ・どの操作で版を更新したか |

`CASE/revisions/00000000000000000001.json`から版ごとの完全な記録を残す。既存の版を上書きしない。排他ファイルと`expected_revision`により、別の更新があると409を返す。入力欄を保持したまま最新版を読み直して再確認する。途中の.pendingは採用せず、最新の.jsonが壊れていれば黙って古い成功へ戻らない。

ファイルの書き込みと同期後にhard linkで版を確定するローカル方式。DB、クラッシュ復旧、監査証跡の真正性の保証ではない。異常終了後の`write.lock`は、他の書き込みがないことと保存済みの版を確認して手動で扱う。読み込み・保存は4MiB上限。連続運用、大人数、大量ログの試験は未実施。

## 根拠を現在の条件へ使える範囲

条件の版・規則、宣言した依存先の値を照合する。違い、不足、観測の食い違いがあればUnknownとして理由を示す。最後に取り込んだ試行を選び、古い成功へ戻って欠落を埋めない。条件文・規則を変えると、以前の回答も未回答へ戻し、古い版に回答を残す。

標準の実行条件はmanifestとtarget.jsonから取り込む。追加の依存先は事例の宣言値をコピーし、実行記録で観測した値とは区別する。画面のcontext更新は実際の環境変更を実行しない。自動的な本番環境の監視や、コード変更から全依存先を推定する機能もない。手動の対応づけが正しいかを別途調べる必要がある。

`case import`は完了した試行のmanifest/eventsと、存在する場合は固定版アダプターのtarget/eventsをコピーする。元の試行を後から書き換えても保存済みの根拠は変わらない。truth.json、stored.json、adapter-truth.json、adapter-assessment.jsonを判定に使わない。

```bash
cargo run -- case import cases/review /absolute/path/to/run \
  --condition local-index --actor 実行者 --reason 固定版の観測を取り込む \
  --use-run-context true
```

local-indexは事前に作る。[実アプリ適用手順](vitalsensing-local.md)の自動確認スクリプトも利用できる。`--use-run-context true`は取り込む試行の条件を現在の宣言にする操作。falseでは現在の宣言と一致しなければUnknownになる。

## 判定方法と次の確認

| 規則 | 判定できる限定条件 |
| --- | --- |
| demo_save | 同じ試行・データ・送信試行のサーバーの書き込み・同期成功 |
| local_index_uploaded | 対応する固定版・試行・発行キーについて、模擬索引のuploadedへの更新を観測したこと |
| manual_only | 自動判定は未定義。回答や終了コード0からSatisfiedへ変えない |

既存の二つの規則は定義済みの条件文だけに使える。「管理者が閲覧できる」へ名前を変えて流用することは拒否する。外部条件の判定方法の追加は、実際の条件と観測の対応が決まってから行う。

未回答には質問、古い根拠には再試験、食い違いには照合、観測不足には追加観測などを、少数の明示的な規則で提案する。提案と人の決定は別の記録。最適な質問選択や未知の見落としの発見能力は検証していない。

## 比較の準備

`case export`は同一のinput.jsonを4条件へ含める。baseline.mdは通常の条件・出所・記録、checklist.mdは通常の確認手順、linked.mdはその情報から生成した対応と失効理由・行動提案、without-links.mdは根拠参照と説明を外した表示。元の情報を削らず、通常の方法でも手作業・既存ツールで整理できる。

これは表示の比較準備。判定器の構成要素を外す実験、有力な既存ツールの再現、goat/YAGIとの比較、利用者評価は別に必要。独立した参照項目、同じ時間・作業予算、参加者、順序効果を確定してから評価する。両者の回答の一致と正しい理解、安心感と誤った判断、確認時間を分ける。

## ローカル画面の境界

RustにHTML・JS・CSSを埋め込み、127.0.0.1へだけbindする。実行時の操作トークン、同一OriginとlocalhostのHost、JSON形式をPOSTで検査する。HTTP経由では任意のコマンドやファイルを受け付けず、外部試行のimportはCLI専用。画面からは定義済みの合成TCP試行のみ実行する。

Linux/macOSの`/dev/urandom`を使う。Windows、外部共有、参加者認証、アクセス権ごとの公開範囲は未対応。一般的なWebサービスとしてインターネットへ公開する仕様ではない。

## 継続で追加した画面と汎用の入口

確認状況の件数、観測で確認していない範囲、現在の判定には使えない古い根拠を表示する。更新や最新版の読み直しで、未保存の回答・質問・条件編集と選んだ確認事項を保持する。ページ全体の再読み込み・終了後の下書き保存は未対応。

`case init --template general --id general-001 --title 通知の確認`で初期の医療条件や練習用の発言を持たない事例を作れる。条件を追加しても自動判定は未定義。比較の変更と反例は[確認手順の再現](method-reproduction.md)、汎用版の残る条件は[11月の計画](general-release-plan.md)を参照する。
