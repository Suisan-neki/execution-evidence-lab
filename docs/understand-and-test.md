# 理解と試験の画面

更新日：2026年10月14日。ブランチ `feat/understand-and-test-flow` で実装した画面の操作、判定の規則、限界を記録する。Codexが選んだ試作の仕様で、本人や医療機関が採用した業務要件ではない。

## 起動

```bash
cargo run -- app data/app --port 8765
```

表示された `http://127.0.0.1:8765` を開く。データの保存先（例では `data/app`）に、事例（`case`）、読取記録（`snapshots`）、取得したリポジトリ（`repositories`）、試行（`case/runs`）を置く。既存の事例や `cases/` 以下は読まない。

任意で次の環境変数を指定する。どの値もサーバーだけが読み、画面には返さない。

| 変数 | 内容 |
| --- | --- |
| `EEL_GITHUB_TOKEN_FILE` | GitHubのAPIの利用上限を広げるための認証情報を書いたファイル。未指定のときは認証なしで読む（1時間に60件） |
| `EEL_AI_BASE_URL`、`EEL_AI_MODEL`、`EEL_AI_API_KEY_FILE` | OpenAI互換のAIの接続先。3つそろわないときは「未設定」と表示し、静的解析だけを使う |

`--execution-mode bubblewrap` はLinuxでbubblewrapが使える場合だけ選べる。既定はlocal方式で、OSによる隔離は行わない。

## 利用者の操作

1. **リポジトリを開く**。URLと、任意のブランチ・タグ・コミットを入力する。基盤はGitHubのAPIでコミットを固定し、ファイル一覧と、README・設定・入口を優先した最大24件の本文を読む。解析の対象はPython、JavaScript・TypeScript、Rustのコードと、README・設定・GitHub Actions・cramのテスト。読んだ範囲、取得に失敗したファイル、読んでいないファイルとその理由（初回の読取範囲外、サイズ上限、解析に対応していない種類）を表示する。読んでいないファイルも、画面から本文を開ける。URLを入力しただけでは、対象のコードもインストール用のスクリプトも実行しない。
2. **ソフトウェアを理解する**。目的、起動のしかたと入口、主な構成と役割、入力から保存・送信までの流れ、既存のテスト、コードを読むだけでは確かめていないことを表示する。各項目に「コードで確認」「作者の説明」「解析の推測」のどれかを文字で付ける。入口からの流れは呼び出し候補をたどった推測で、実行した経路としては示さない。
3. **質問する**。「タスクはどこに保存される？」「保存できなかったらどうなる？」のような質問から、関係する記述と関数を示す。関数ごとに、引数、戻り値、分岐、発生させる例外と捕捉する記述、副作用、呼び出す関数、呼び出し元の候補、関係するオプション、既存のテストでの言及を出す。必要なら未読のファイルを最大8件追加で読む。見つからなかったことと、この結果の限界も表示する。
4. **期待を書く**。「誰が何をしたとき、何がどうなってほしいか」を自分の言葉で書き、「この動作を確かめる」で記録する。テストの例は参考として表示するだけで、期待として保存しない。技術者は、コードの行と、どう確かめるかを対応づける。記録を読んだ人は「内容を確認したことを記録する」で確認を残す。食い違いの指摘、答えが必要な質問、回答、対応も同じ記録に残る。
5. **実際に試す**。起動ファイル、引数、保存先、後から読み出すコマンド、故障の種類、判定の条件、待機の上限を入力する。画面は実行する内容（コミット、起動のしかた、入力、保存先、故障、観測の方法、隔離の範囲）を表示し、利用者が「この内容で試す」を押したときだけ実行する。
6. **結果を確認する**。試したこと、期待したこと、観測した結果、観測の出所、判定（条件を満たす・条件を満たさない・判定できない）、判定の理由、次に確認すること、確かめていないことを表示する。技術的な詳細（コマンド、終了コード、出力、保存先の内容、試験の設定）は同じ記録から開ける。結果から、対応づけたコードと起動ファイルへ戻れる。結果への質問・異論も書ける。
7. **修正した版で再試験する**。修正したブランチ・タグ・コミットを読み込み、対応づけたコードの行を新しいコミットで確かめてから試す。前の試行と判断の記録は残る。二つの試行を比べると、コード参照、試験の設定、終了コード、判定条件ごとの結果などの違いを表示する。結果が変わっても、修正が原因だとは断定しない。

画面の上部には、現在のリポジトリ、コミット、関数、期待、試行を常に表示する。

## 記録と確認

- 記録の文には、記入者、記入した時点の事例の版、記入時の条件の版を基盤が付ける。画面から送られた記入者や確認の情報は使わない。
- 確認の状態は「未確認」「一方の役割だけが現在の条件の版で確認した」「運用担当と開発者の両方が、現在の条件の版で確認した」「確認後に条件が変わり、再確認が必要」の4つ。人の確認だけから計算し、「合意済み」とは表示しない。役割は記入者の自己申告。
- 期待の文を直すと条件の版が上がる。前の版での確認と試行は消えず、現在の版には数えない。
- 古い版の記録をもとにした更新は409で拒否する。画面は「最新の記録を読み直す」を表示する。

## 試行の判定

試行には、判定の条件を一つ以上付ける。条件ごとに「確認する範囲」「観測の方法」「期待」を持つ。

| 観測の方法 | 観測の出所 |
| --- | --- |
| 終了コード、標準出力、標準エラー | 対象プログラムの報告 |
| 保存先の内容 | 試行の後に、基盤が保存先のファイルを直接読み出した結果 |
| 後からの読み出し | 書き込んだプロセスの終了後に、別のプロセスで対象の読み出し機能を動かした結果 |

判定は次の順に決める。

1. 固定コミットのファイルが試行中に変わっていたら、判定できない。
2. 指定した故障が実際に効いていなければ、判定できない。
3. 同じ範囲の条件の結果が食い違っていたら、判定できない。同じ範囲には、同じことを別の方法で確かめる条件をまとめる。
4. 期待と異なる観測が一つでもあれば、条件を満たさない。
5. 観測できていない条件が一つでもあれば、判定できない。
6. すべて期待どおりなら、条件を満たす。

終了コードだけの条件では試行を受け付けない。現在の判定は、現在の条件の版と試験の設定に一致する最新の試行だけから決める。前の試行の成功で、最新の試行の欠けた観測を補わない。

## 故障の与え方

| 故障 | 基盤が行うこと |
| --- | --- |
| 保存先を書き込み不可にする | 試行の前に保存先へ空のファイルを作り、書き込み権限を外す。書き込めないことを確かめてから対象を起動する。書き込めてしまう環境（管理者権限など）では、故障が効かなかったとして判定できないにする |
| 保存先に同名のディレクトリを置く | 試行の前に保存先と同じ名前のディレクトリを作る |
| 基盤による保存先の読み出しを止める | 対象は通常どおり動かし、試行後の保存先の読み出しだけを止める。観測の欠落を成功と扱わないかを確かめる |
| 外部への通信を遮断する | bubblewrap方式でネットワークを持たない環境で起動する。local方式では受け付けない |
| 保存先のディレクトリを書き込み不可にする | 保存先を置くディレクトリの書き込み権限を外し、書き込めないことを確かめてから起動する。受信側が保存先を作る対象に使う |
| 待つプロセス（受信側など）を起動しない | 待つプロセスを起動せずに、操作するプロセスだけを動かす |

## 依存先と待つプロセス

- 依存先は、リポジトリと40文字のコミットで指定する（例：`pydicom/pydicom 20aa4b73aef76bffb6fbc46a8827588dfa9bb89d src`。3つ目は読み込み先のディレクトリ）。基盤が固定コミットだけを取得して読み込み先に置く。インストールやビルドは行わない。
- 起動のしかたは、ファイル、モジュール（`python -m`）、pyprojectのscriptsから選ぶ。
- 待つプロセスは、操作するプロセスより先に起動し、基盤が選んだポートへ接続できるまで待つ。引数の `{{port}}` はそのポート、`{{source}}` は固定コミットの複製の場所に置き換わる。試行の後に基盤が止め、出力は「待つプロセスの出力」として別に観測する。

## 隔離の範囲

- 対象は試行ごとに新しい作業ディレクトリで動く。固定コミットのファイルは読み取り専用で複製する。
- 環境変数は消し、HOMEも作業ディレクトリにする。試験用の値は試行ごとに `eel-test-` で始まる新しい架空の値を作る。
- 依存パッケージはインストールしない。package.jsonのscripts、Makefile、GitHub Actionsのコマンド、cramのテストは表示するが、画面からは実行しない。
- local方式はOSによる隔離を行わない。対象が絶対パスで書き込む処理や、外部への通信は止められない。

## AIによる説明

AIの接続先を設定した場合だけ「AIの説明も求める」を表示する。基盤は質問に関係する固定コミットの行（最大48KB）だけを送り、応答が示したファイルと行が読取記録に存在するかを照合する。照合は説明の正しさを保証しない。未設定・接続の失敗・形式の誤りはそのまま表示し、固定文や架空の応答で置き換えない。静的解析の結果は、AIの状態にかかわらず表示する。

## 実行に対応する範囲

Python 3とNode.js（JavaScript）の起動ファイルだけを実行する。ほかの言語は「実行は未対応」と表示し、理解と試験の準備に使う情報だけを示す。TypeScriptは変換が必要なため未対応。

## 未確認の範囲

- 実際の利用者（医療機関の運用担当、開発者）による操作と理解は未評価。この画面での検証は、Codexが架空の利用者として操作した確認に限る。
- 公開リポジトリ1件（sjl/t）での確認であり、ほかのリポジトリで同じように理解・試験できることは保証しない。
- 静的解析は名前と参照宣言による候補で、型や動的な呼び出しは解決しない。
- 複数の利用者が別の端末から使う運用、認証、外部への公開は対象外。
