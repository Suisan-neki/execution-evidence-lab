# リポジトリから構成図・疑問・検証へ進む

2026年10月21日の本人の指摘を受けた変更。利用者の順序は、技術者／非技術者の選択→GitHub読取→構成図→不安や疑問の整理→検証と改善。

同日の追加指摘を受け、ファイル単位の参照図から、サービスと役割・接続をまとめる図へ変更した。非技術者には役割と情報の流れを、技術者には同じ部分の内部の処理や技術・接続を説明する。[抽出方法と限界](repository-architecture.md)、[設計と完了条件](system-architecture-design.md)を参照する。

## 入口と構成図

`cargo run` で利用者向け画面を開く。最初は立場の選択だけを示し、次にURLを入力する。デモ、モードの記入者、設定理由、試験用構成の選択を入口に置かない。立場はこのブラウザでの自己申告で、権限や本人確認を表さない。

固定コミットのサービス定義とコードを対応づけ、箱と接続線に設定・コードの行への参照を残す。実線は要求やデータのやり取りの記述、点線は設定・起動の依存を表す。接続を選ぶと、根拠と推定した範囲を読める。線を動作の成功の証明にしない。

同じアプリ内の処理は説明へまとめ、全体図をファイルごとの箱で埋めない。立場を変えても識別子と配置を保つ。図を拡大・縮小して読める。読み取れない部分を示し、構成を特定できない場合も全体への疑問を残せる。実際の配置や対応外の構成の抽出は未完成。

## 疑問と検証

図の箱や接続線を選び、説明を読んで疑問を書く。選ばなければシステム全体への疑問になる。部分ごとの書きかけを同じブラウザのセッションに保持し、保存に失敗しても消さない。対象リポジトリとコミット、選んだ部分の情報を、既存の発言記録に保存する。別のリポジトリの疑問を混ぜない。以前のコミットへの疑問には、その版への記録であることを示す。

疑問は未回答の発言で、期待や判定に自動変換しない。利用者が検証したい動作を具体的に記入したとき、未検証の確認事項として保存する。全体への疑問に特定のコードを勝手に割り当てない。検証方法が未定義の間は `manual_only` を維持する。

検証の起動・観測・判定条件は `/workbench` に残した技術者向け画面で設定する。読み込んだ固定コミットと確認事項を引き継ぐ。移動や再読込だけでは実行しない。実行は内容を確認して開始した場合に限る。結果の確認、対応判断、改修版の再試験は既存機能を使う。画面上部から元の構成要素・接続と疑問へ戻れる。

立場を変えても事例・試行・判定は書き換えない。AI対話の接続は未実装。既存の任意AIによるコード説明は技術者向け詳細画面に残り、新しい疑問整理の機能と区別する。

## 検証

`cargo build --locked` の後に `npm run test:journey` を実行する。保存済みの架空リポジトリを実Rust APIから読み、図の作成、疑問、競合、検証設定への移動、対象の分離、画面幅を確認する。実参加者による理解や操作性の評価は別に必要。
