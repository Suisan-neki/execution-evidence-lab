# リポジトリから構成図・疑問・検証へ進む

2026年10月21日の本人の指摘を受けた変更。利用者の順序は、技術者／非技術者の選択→GitHub読取→構成図→不安や疑問の整理→検証と改善。

## 入口と構成図

`cargo run` で利用者向け画面を開く。最初は立場の選択だけを示し、次にURLを入力する。デモ、モードの記入者、設定理由、試験用構成の選択を入口に置かない。立場はこのブラウザでの自己申告で、権限や本人確認を表さない。

読取APIで固定したコミットのコードから構成候補を作る。図の各部分にファイル・行への参照を残し、読み取れなかった範囲と図からの省略を説明する。線はファイル間の参照宣言で、実行順序や通信の成功を表さない。解析対象外の言語や未読のコードから構成を創作しない。構成を作れない場合はその理由を示し、全体への疑問を記入できる。

現在の候補は最大18ファイル。既存の読取範囲・解析の上限を維持する。実際のサービス配置、外部システム、動的な接続を含む完全なシステムアーキテクチャは、まだ抽出できない。

## 疑問と検証

図の部分を選び、説明を読んで疑問を書く。選ばなければシステム全体への疑問になる。部分ごとの書きかけを同じブラウザのセッションに保持し、保存に失敗しても消さない。対象リポジトリとコミット、選んだ部分の情報を、既存の発言記録に保存する。別のリポジトリの疑問を混ぜない。以前のコミットへの疑問には、その版への記録であることを示す。

疑問は未回答の発言で、期待や判定に自動変換しない。利用者が検証したい動作を具体的に記入したとき、未検証の確認事項として保存する。全体への疑問に特定のコードを勝手に割り当てない。検証方法が未定義の間は `manual_only` を維持する。

検証の起動・観測・判定条件は `/workbench` に残した技術者向け画面で設定する。読み込んだ固定コミットと確認事項を引き継ぐ。移動や再読込だけでは実行しない。実行は内容を確認して開始した場合に限る。結果の確認、対応判断、改修版の再試験は既存機能を使う。画面上部から構成図と疑問へ戻れる。

立場を変えても事例・試行・判定は書き換えない。AI対話の接続は未実装。既存の任意AIによるコード説明は技術者向け詳細画面に残り、新しい疑問整理の機能と区別する。

## 検証

`cargo build --locked` の後に `npm run test:journey` を実行する。保存済みの架空リポジトリを実Rust APIから読み、図の作成、疑問、競合、検証設定への移動、対象の分離、画面幅を確認する。実参加者による理解や操作性の評価は別に必要。
