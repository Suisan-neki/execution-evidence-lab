# 研究と実装のロードマップ

更新日：2026年10月7日。全体のIssueツリーは[全体計画#5](https://github.com/Suisan-neki/execution-evidence-lab/issues/5)。小さなアプリの4条件は基盤の接続確認であり、地方版未踏のゴールは実システムへの適用、手法、改修と再検証、比較評価までを含む。

## 研究で目指すこと

「技術者と非技術者で目線の高さを合わせる」「技術者が安心して世に出せる」を前に出す。初期対象の医療機関の運用担当と開発者が、業務上の条件とシステムの状態、根拠、未確認事項を対応づけて判断できる状態を目指す。持ち込まれた既存システムで、発言、コード、実行結果、改修の差分をつなぎ、不明点に応じて次の質問・試験・観測追加を選ぶ手法を検討する。

初期題材はVitalSensing。近接研究との違い、有力な既存手法の組み合わせとの比較、構成要素を外す比較、別事例、他者の理解、導入と保守の負担を評価する。新規性や医療機関での有効性は未検証。

## 実装と理解を分ける

本人の指示により、2日間ほど実装をまとめて進め、3日間ほど理解・レビュー・修正に使う。関連する複数のIssueを一つの動くPRで扱い、役割別のモジュール、判断理由、実行記録を残す。機能ごとの理解確認を待つことを次の実装の条件にしない。マージは本人の明示的な指示で行う。

実装前に最新の作業ブランチと本人の変更を確認する。試作に必要な通常の方法はCodexが選ぶ。実装の仮の選択を医療機関の採用済み要件にしない。取得できない業務情報や実環境の対応は未確認として残し、独立して進められる作業を継続する。

Issueは判断・実装・検証ごとに小さく保つ。親Issueから子を参照し、子から親とPRへ戻れるようにする。status:doingは作業中、status:reviewはレビュー待ち、status:blockedは必要な情報・依存先待ち。PR提出とマージ、実行確認と比較評価をそれぞれ区別する。
