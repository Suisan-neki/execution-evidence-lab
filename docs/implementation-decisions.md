# 今回の実装で選んだこと

2026年10月6日の実装期間。ここに記すのはCodexが試作を進めるために選んだ仕様と理由であり、採用済みの医療業務の要件ではない。

| 選択 | 理由 | 確認した範囲と残ること |
| --- | --- | --- |
| CLI、localhostのTCP | 操作から保存・表示までを実際に動かせる | GUI、端末と遠隔サーバーは未再現 |
| 長さ付きJSON、64KiB上限 | 分割されたTCP読み出しでも終端を決め、過大な受信サイズを拒否する | 書き出し前のJSON直列化には入力分のメモリを使う |
| I/Oと接続待ち各1000ms | 実験が無期限に待たない | 高負荷環境では正常処理も待機上限に達しうる |
| 試行ごとのcreate_newとsync_all | 過去の記録を上書きせず、ファイル書き込み成功を限定して扱う | ディレクトリ同期、原子的更新、電源断復旧は未保証。DBではない |
| 試行・データ・送信試行のID | 時刻の近さで関連を推測しない | 1件・1送信限定。再送、複数端末、分散時計は未対応 |
| MutexでJSONL記録を直列化 | 同時の書き込みで行を混ぜない | 計測は処理時間へ影響する。非計測時との負担比較は#50で未実施 |
| 通信断用TCPゲート | 要求を実際に受け、サーバーへ渡さず切断する | OSレベルのパケット損失ではない |
| 保存開始前の人工失敗 | 受信済みと保存成功を分けて確かめる | 実ディスク障害・部分書き込みの再現ではない |
| 保存の観測のみを省く | 保存失敗と観測不足を分ける | ログ基盤全体の欠落・再接続は未再現 |
| 判定器にTruthを渡さない | 答え合わせの情報を観測の代わりに使わない | 参加者評価用のCLIではTruthを見せない手順が必要 |
| 出来事の番号・順序を検査 | 壊れたJSON、重複・欠番、時間の逆転を黙って採用しない | 書き換えられたログの真正性を保証する署名はない |
| 条件の変更はUnknown | 意味が変わった条件へ古い規則を当てない | 対応する判定規則を増やす仕組みは今後必要 |
| ソース指紋をビルド時に付ける | src、build.rs、Cargo.toml、Cargo.lockの変更を識別する | FNV-1aは暗号学的検証ではない。外部対象、SDKの実体、OS全設定は含まない |
| compareで差分を示す | 過去の結果と現在の実行条件を区別する | 設定一致は将来の保証ではない。captureは対象コード未識別のため証拠一致を常にfalseにする |
| 外部プロセスの出力をファイルへ流す | 大量出力をメモリにためず、子孫が持つパイプによる待機を避ける | ディスク消費上限・隔離・外部状態の初期化・子孫の停止は未対応 |
| 固定版ハンドラーの依存先を注入 | 元の処理を動かしつつAWS資源を使わず一経路を試す | 実S3、DynamoDB、Cognito、iOS、管理画面は別に確認する |

異常終了などで記録出力を完了できなければcomplete.jsonは作られない。途中のファイルを残し、成功した試行として扱わない。

次の確認の選択は少数の明示的な規則による試作で、学習済みの質問選択や新規アルゴリズムではない。#65・#93の文献比較と、#86・#87の比較評価へ接続する。

## 理解とテストの入口の修正

本人の2026-10-07の指定に合わせ、GitHubを読む理解画面とテスト結果を記録する画面を分けた。保存試験の記録画面から始まっていた入口を修正する。

公開APIとraw.githubusercontent.comは利用者のブラウザから読む。GitHubのトークンや取得コードをサーバーへ送らない。コミットを固定して出所の行へ戻る。対象コードをスキャンだけで実行しない。

最初の読解は簡易な宣言・参照の抽出と作者の説明の表示。静的な参照関係を実際の実行経路としない。未知の構文や未読ファイルがあるため完全な理解とは扱わない。コードを条件の出所へ渡しても試験方法は未定義として始める。

以下は今回より前に進めたテスト基盤の選択。

- 共通比較入力からdecisions.basisの自動判定理由・行動提案を除く。元の事例と判断履歴は変えず、人が記入した判断・理由は双方の資料へ同じように渡す。説明を外す表示へ説明が混入する問題を避けるため。
- 通常の確認手順の参照実装をNode.jsで別に作り、同じinput.jsonから限定した保存条件を再現する。13事例の一致は規則の再現確認であり、優位性や人の作業時間の検証ではない。
- 発行前の索引成功と対象不明の失敗をUnknownにする。成功を使う前に対象と順序を照合する必要があるため。実ハンドラーの新しい障害を発見した意味ではない。
- 空の汎用事例は既存Workspaceを再利用する。条件・質問・回答を自動で作らず、医療特化の要件待ちでも一般の事例を開始できる。アダプター完全分離は次の作業。
- 画面の再描画時は未保存の入力と選択を保持する。未編集の条件文・規則・依存先は最新版へ更新する。ページ終了後の下書きの永続化は含めない。

## 10月13日の固定版の実行・汎用観測

- Gitのコミットから通常ファイルをコピーして、未コミットの作業ファイルを実行しない。origin・コミット・起動ファイル・参照ファイル・行範囲を照合する。symlink・submoduleは扱わない。
- Node.jsとPythonを明示し、依存パッケージは自動で導入しない。JSON入力・引数・観測名・対象を試験設定に保存する。資格情報を含む親の環境変数を引き継がず、試行用の環境変数だけを渡す。Pythonのbytecodeキャッシュが固定版へ作られないようにする。
- 対象コードの観測を共通のJSONLで受ける。識別子・順序・参照先・行を照合し、欠落、別試行、食い違いから成功を補わない。観測の呼び出し元はプロセスの申告で、独立した実行トレースではない。
- 条件ごとの依存先へ試験設定・ランタイム・入力・方式を保存する。違う条件の試験設定を全体の共通値として混ぜない。事例の変更と試行の取り込みは競合を検査し、実行中の変更は上書きしない。
- localは自分で確認したコードの接続用。OSの隔離、子孫プロセス全体の停止、外部状態の復元は保証しない。Linuxのbubblewrapはnamespace・読み取り専用の固定版・試行用workを使い、起動不能時にlocalへ切り替えない。
- 次の確認は明示的な規則で選ぶ。実行・終了失敗は起動設定と標準エラーの確認、固定版の変化や無効な観測は出所の照合、正常終了後の観測欠落は選択した観測名・対象の出力箇所の確認へつなぐ。未回答の利用条件と古い根拠はそれぞれ質問・再試験を優先する。新規性や最適な質問選択を示した意味ではない。

仕様・制限は[pinned-execution.md](pinned-execution.md)。本人の仕様採用、実運用の条件、実参加者の理解、比較での優位性は未確認。

## 画面からの固定版実行（10月13日、#128）

- 起動時に一つのGitリポジトリと方式を指定した場合だけ、画面から固定版を実行する。通常のレビュー画面から任意のファイル・コマンド・取得先を指定する操作は追加しない。
- 一件を別スレッドで実行し、HTTPの閲覧を処理できる状態にする。同じサーバーの二重起動をMutexで拒否する。複数サーバー全体の排他や実行の中断・再開は含まない。
- 受付、起動直前、結果取り込み時に事例の版を照合する。途中の変更では試行を残し、現在の事例を上書きしない。終了・取り込み完了と、業務条件の成功を区別する。
- 完了状態を読んでから事例を読み直す。古い事例の判定を取り込み完了の結果として見せないため。編集中の入力は既存の下書き保持を使う。
- 実行ボタンと設定の保存は同じ入力検査を使う。方式・リポジトリパスは起動時の設定を使い、ブラウザからの上書きを受け付けない。localはOSの隔離ではない。

これは接続操作の試作で、任意アプリの自動計測、医療業務の要件採用、研究の有効性を示すものではない。

## 読み込みの別名と呼び出し元（#129）

- 読み込み宣言のローカル名と参照先の名前を記録し、候補の宣言と対応づける。未読ファイルに仮の関数を作らない。参照先を追加で読むと、同じ固定版の解析を更新する。
- 型や動的な束縛を解決しないため、呼び出し先・元は常に候補として示す。引数や簡単な局所宣言に同名の記述があれば、対応づけを保留する。複雑なスコープの完全な検査ではない。
- 呼び出し元の探索は最大400関数、表示は最大80件にする。未読のコードと上限を表示し、結果がないことを呼び出しがない証明にしない。
- 同じ解析モデルの関数範囲と案内を再利用する。追加読取・版更新でモデルを作り直すため、旧版の対応を新しい版へ流用しない。
- Pythonの拡張子省略を同名のJavaScriptファイルへ解決する反例を修正し、言語ごとの参照先候補を使う。再export・パッケージ内部・動的呼び出しは未対応。

## 汎用バックエンドv1（#133）

- 医療固有の固定対象の検査と模擬索引の判定を`src/adapters/vitalsensing.rs`へ分離し、既存の保存・固定版実行・医療アダプターの判定を維持する。
- 外部からの観測を`reported_assertion`として追加する。基盤による固定版実行とは別の型にし、報告者・出所・構成を保存する。順序・識別子・条件の版と参照先を照合し、欠落・未完了・食い違いはUnknownにする。
- APIはlocalhostの`/api/v1`とし、トークンを新規の所有者専用ファイルへ保存する。ブラウザのOriginがある場合は同一Originを要求し、OriginのないCLIはトークンを要求する。従来の画面向けAPIは維持する。
- Rust側の比較は保存した生のJSON値を比較し、整数の精度をJavaScriptへ依存させない。サーバーとCLIで同じ判定・比較を使う。
- バックアップは全版の記録と判断当時の根拠を検査し、新しいディレクトリへ復元する。途中の復元はマーカーで未完了と分かるようにし、既存を置き換えない。作業領域や答え合わせ用のファイルは別に管理する。
- コード読取・静的解析は既存のJavaScriptモジュールを埋め込み、信頼するNode.js処理からJSONで呼ぶ。対象リポジトリのコードを起動しない。30秒の待機上限と入出力の上限を設ける。
- HTTPは最大16件を別スレッドで扱い、途中のリクエストやネットワーク読取でほかの閲覧を止めない。事例への書き込みは従来の排他と版照合を使う。

## 理解と試験の画面（10月14日）

使い方と判定の規則は[understand-and-test.md](understand-and-test.md)、画面の部品は[design-system.md](design-system.md)。次はCodexが試作のために選んだ仕様で、本人が採用した業務の要件ではない。

- 対象の例に [sjl/t](https://github.com/sjl/t) を選んだ。Python標準ライブラリだけで動き、依存関係のインストールが要らない。作業用ディレクトリのファイルへ書き、後から同じコマンドで読み出せるため、「受付」「書き込み」「後から読み出せた」を別々に観測できる。コミット `70817fd` では保存に失敗しても終了コードが0になり、`815ccaf` で1になる。修正前後の比較を、対象の実際の履歴で確かめられる。
- URLを入力したときは、GitHubから一覧と本文を読むだけにする。試験用の取得（`git fetch --depth=1` で固定コミットだけを管理用ディレクトリへ取得）と実行は、利用者がそれぞれのボタンを押したときだけ行う。依存関係のインストールは行わない。
- 読んだ固定コミットのファイルをデータの保存先の `snapshots/` に残す。40文字のコミットを指定して開き直すときは、保存した内容を使い、GitHubへ再度問い合わせない。ブランチ名やタグは指す先が変わるため、毎回問い合わせる。
- GitHubの問い合わせ回数の上限に対応するため、`EEL_GITHUB_TOKEN_FILE` で読み取り用のトークンを指定できる。トークンはサーバーが読み、環境変数を消した読み取り処理（Node.js）へだけ渡す。画面・記録・ログには出さない。GitHubのトークンは長さと形式が変わるため中身を解釈せず、要求ヘッダーを壊す空白・改行・制御文字と、4096文字を超えるものだけを拒否する。
- 実行環境は、PATHで見つかった `node`・`python3` に実体のパスを尋ねて決める。pyenvなどのシェルスクリプトは、環境変数を消した試行で動かないため。見つからない、または起動できない場合は、画面に「利用できない」と理由を表示し、実行ボタンを止める。
- 期待・実装の説明・指摘・質問は、基盤が記入者・事例の版・条件の版を記録する。確認は名前と役割を添えて、記録した人とは別に残す。運用担当と開発者の両方が現在の条件の版で確認したときだけ「両者が確認済み」と表示する。条件を変えると「再確認が必要」に戻る。名前と役割は利用者の自己申告で、本人確認は行っていない。
- 「合意済み」という状態は作らない。判断の記録は、記入した人の判断として表示する。
- 一つの判定の範囲を、別々の方法で観測した結果が食い違う場合は「判定できない」とする。そのため故障の試験案では、終了コード・エラー表示・書き込みを別の範囲に分ける。
- AIの説明は、サーバーで設定（`EEL_AI_BASE_URL`・`EEL_AI_MODEL`・`EEL_AI_API_KEY_FILE`）したときだけ使う。固定コミットの抜粋を渡し、返った説明の引用ファイル・行が実在するかをサーバーで照合する。未設定・失敗のときは、その状態を表示し、固定文で補わない。静的な解析と質問への回答は続けて使える。

確かめていないこと：医療業務での利用条件、実際の運用担当と開発者がこの画面で理解できるか、ほかの言語・依存関係を持つ対象での試験、複数人の同時編集、外部公開時の認証。

## 固定した依存先と複数のプロセス（#137）

#138の一つ目。対象の例に [pynetdicom](https://github.com/pydicom/pynetdicom)（v3.0.4、`2692cb9`）と、依存先の [pydicom](https://github.com/pydicom/pydicom)（v3.0.2、`20aa4b7`）を選んだ。DICOMの送信（storescu）と受信（storescp）が別のプロセスで、受信側が保存できずに失敗の状態（0xA700）を返しても、送信側の終了コードは0になる。終了コードだけでは保存を判断できないことを、医療系の実際のOSSで確かめられる。次はCodexが試作のために選んだ仕様で、本人が採用した業務の要件ではない。

- 依存先は、利用者が指定したリポジトリと40文字のコミットだけにする（最大8件）。基盤が `git fetch --depth=1` で取得し、ファイルを試行ごとに読み取り専用で複製する。`pip install`、ビルド、対象のインストールスクリプトは実行しない。版の範囲の解決や、依存先の依存先を自動で取得することもしない。
- pydicomなどは `importlib.metadata` で自分の版を読むため、インストールしないと起動できない。基盤が、固定コミットの `pyproject.toml` の `[project]` に書かれた名前・版・scriptsだけから、最小の配布情報（`*.dist-info`）を作る。`dynamic` で版や名前を決める対象には作らず、作らなかったことを記録する。作った配布情報は記録に残し、インストールした結果とは扱わない。
- Pythonは `-S -P` で起動し、読み込み先を「対象の読み込み先」「依存先」「生成した配布情報」の順に固定する。利用者の環境のsite-packagesと作業ディレクトリを読み込まないため。`-P` を使えないPython 3.10以前では、依存先を使う試行を受け付けない。
- 起動のしかたは、ファイル・モジュール（`python -m`）・pyprojectのscriptsの3つ。モジュールとscriptsは、固定コミットのファイルに実在するかを試行の前に確かめ、実際に起動したファイルを記録する。
- 受信側のような先に起動して待つプロセスは、試行ごとに基盤が空いているポートを選び、引数の `{{port}}` に入れる。ポートへ接続できたら準備できたとし、待機の上限（最大60秒）までに準備できない、または停止の前に終了した場合は判定できないとする。ポートを選んでから起動するまでに別のプロセスが使う可能性は残る。停止は終了のシグナル（SIGKILL）で行うため、受信側の終了時の処理は観測しない。準備の確認のための接続を、受信側は1回の接続として扱う。
- 待つプロセスの出力は、操作するプロセスの出力とは別の観測の方法（待つプロセスの出力）にする。どちらも対象プログラムの報告で、基盤による保存先の読み出しとは区別する。
- 故障に、保存先のディレクトリを書き込み不可にする、待つプロセスを起動しない、を加えた。前者は書き込めないことを確かめてから起動し、書き込めてしまう環境では故障が効かなかったとする。
- 引数の `{{source}}` は、固定コミットの複製の場所に置き換える。対象のテスト用ファイル（pynetdicomの `CTImageStorage.dcm`）を入力に使うため。
- bubblewrap方式では、プロセスごとに別のネットワークになり、待つプロセスへ接続できない。そのため待つプロセスのある試行は、local方式へ切り替えずにエラーにする。

確かめていないこと：bubblewrap方式での複数プロセスの試行、PythonのC拡張やビルドが必要な依存先、Node.jsの依存先、医療機関の稼働環境でDICOM通信を試す条件（接続先、AEタイトル、保存先の扱い）。

## 試験専用コンテナ（#139）

#138の二つ目。OpenEMR（PHPとMariaDB）と、OHIF用の画像サーバー（Orthanc）を、本基盤から準備・起動・準備完了の確認・停止する。次はCodexが試作のために選んだ仕様で、本人が採用した業務の要件ではない。

- イメージは `@sha256:` と64桁のダイジェスト付きだけを受け付ける。タグだけでは起動しない。OpenEMRは公式の `docker/production/docker-compose.yml`（コミット `d7ecc612e166c6f9f3adc9f50bc9f8cc68cac701`）を読んで、そこに書かれたダイジェストを使った。対象のcomposeファイルをそのまま実行はしない（`80:80` の公開や `restart: always`、名前付きボリュームの再利用を避けるため）。
- 試行ごとに新しいネットワーク・ボリューム・コンテナを作り、ラベル `eel.managed=1` を付ける。待ち受けは `127.0.0.1` だけに公開し、ホスト側のポートは基盤が選ぶ。引数の `{{port:名前}}` に入れる。終わったら消し、消えたことを確かめる。既存のコンテナは使わない・消さない。
- 準備完了は、TCP・HTTP、またはコンテナ内のコマンド（MariaDBの healthcheck）が成功するまで待つ。HTTPSの準備確認は試験用の自己署名証明書のため検証しない（curl の `-k`）。準備できなければ操作せず「判定できない」にする。
- 操作は、既存のNode.js/Pythonに加えて、基盤がコンテナへ行うHTTP（GET/POST/PUT）を選べる。対象の応答（HTTPの本文）と、コンテナのログと、基盤がデータベースへ `SELECT 1` を送った結果を別の観測として残す。
- 故障は、データベースのコンテナを止める、試験用ネットワークから外す、保存先ボリュームを読み取り専用で載せ直す。効いたことを、停止・切断・書き込みの成否で確かめる。
- Dockerのエンジンに接続できないときは、その理由を返して試行を始めない。localやbubblewrapへは切り替えない。bubblewrap方式とコンテナの組み合わせも受け付けない。

確かめていないこと：Podman、自分でイメージをビルドする場合、OpenEMRの画面からの患者登録（#140）、OHIF Viewer本体のビルド（#141）。OpenEMRの既定アカウント（admin/pass）は使わず、試験用の架空の値にした。

## 2026-10-17 ブラウザの根拠を結果画面から読む（#140）
