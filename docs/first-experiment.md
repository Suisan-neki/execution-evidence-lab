# 小さな再現用アプリによる初期実験

## 目的と今回決めた範囲

検証基盤で、作ったアプリやシステムを試行用の環境で動かす。画面での操作や表示を、端末・通信・サーバー側で観測した出来事と結びつける。関係者が同じ実行記録を見ながら「何を確認できたか」「何がまだ分からないか」「次に何を試すか」を話せる状態を目指す。

最初の実験では、1件のテスト用データを送信する流れを扱う。正常時の結果と、通信断・受信後の保存失敗・観測記録の欠落がある場合の結果を比較する。これらの条件で基盤の働きを確かめる。研究全体では、通信障害以外の問題も対象にする。

試行用のコピーに計測処理を追加する方針と、3種類の異常条件は合意済みである。故障を起こす具体的な方法、記録項目、評価方法は、実装前の設計案として記載する。まだ実装・実験は行っていない。

汎用的な記録と検証の仕組みを先に作り、医療向けアプリでの適用と、実際に患者へシステムを提供する医療者との評価につなげる。

## 入力と出力

初期版は、実行対象のコードと設定、テスト用データ、試す操作、試行条件を受け取る。実行に必要な依存関係と起動手順も入力に含める。環境の準備をどこまで自動化するかは、最初に対応する実行環境を選んでから決める。

出力の中心は、1回の試行をたどれる実行記録とする。記録には画面上の操作や表示と、その操作に関係する出来事のうち、観測できたものを残す。各出来事を結びつけた根拠と、観測できなかった箇所も示す。関係者が記録に確認したいことを書き加え、次の試行条件を決められるようにする。

正常・異常の自動判定は、実行記録から説明できる範囲で補助的に行う。1回の試行だけで「安全に使える」という総合的な結論を返す設計にはしない。

## 初期実験の条件

次の表に、故障を起こす場所とタイミングの案を示す。各試行には新しいテスト用データを使い、開始前の保存状態を記録する。画面が何を表示するかは実測し、成功表示になることを前提にしない。

| 条件 | 起こし方の案 | 評価用に確認する状態 | 基盤で確かめること |
| --- | --- | --- | --- |
| 正常時 | 故障を入れず、1件のデータを送信する | 受信、保存後の読み出し、件数と内容 | 操作・表示・受信・保存の記録を同じ送信の流れとして結びつけ、根拠を示せるか |
| 通信断 | 送信要求がサーバーの受信処理へ届く前に通信を遮断する | 受信処理への到達の有無、保存されたデータの有無 | 端末での送信操作と、実際に到達した範囲を区別できるか |
| 受信後の保存失敗 | 受信処理の後、DBへの保存を確定する前に失敗させる | 受信した事実、保存されたデータの有無 | 「届いた」と「保存された」を区別し、画面表示との対応を示せるか |
| 観測記録の欠落 | 処理は正常に動かし、保存に関する観測記録の一部を取得させない | 別経路で読み出したデータの件数と内容 | 記録がないだけで保存失敗と判断せず、確認できない範囲を示せるか |

通信断には、送信要求が届かない場合と、保存後に応答だけが失われる場合がある。初期実験では、送信要求が届かない条件に固定する。保存後の応答の欠落は、追加条件の候補とする。再送による重複や遅延も、後で同じ記録形式に追加できるようにする。

表の条件は、実験のために意図的に作る。既存の医療向けアプリに同じ不具合があると判断したわけではない。

## 実際の状態を別経路で確認する

検証基盤の正しさは、基盤自身が集めたログだけでは評価しない。試験を管理する側が、故障条件とDBを別経路から読み出した結果などを保管する。結果には照合した時刻、データの件数と内容、確認した範囲を記す。

この確認結果は、基盤や参加者に提示する記録とは分け、評価時の答え合わせに使う。特に観測記録の欠落を試すときは、基盤が取得できなかった情報を確認済みとして扱わない。

保存完了のログ、保存後の読み出し、画面の成功表示では、確認している内容が異なる。どの記録を根拠に何を言えるのかを示す。

## 1回の試行に残す記録

記録形式には、次の項目を含める案とする。

| 記録 | 内容 |
| --- | --- |
| 試行条件 | コードと設定の版、実行環境、初期データ、操作、故障条件、観測期間、追加した計測処理 |
| 出来事 | 出来事の発生元、観測した内容、時刻と順序、根拠となるログなどへの参照 |
| 識別子 | 利用者の操作、送るデータ、個々の送信試行を区別する識別子。再送は別の送信試行として記録する |
| 対応づけ | どの出来事を結びつけたか、その根拠、確認済み・推定・未確定の区別 |
| 観測範囲 | 取得対象に設定した記録、実際に取得した記録、停止や欠落を確認できた範囲、原因が分からない欠落 |
| 次の問い | 確認したいこと、そのきっかけとなった記録、追加で試す条件や観測、次の試行への参照 |

異なる層の出来事を同じ操作に結びつける際は、時刻が近いという理由だけで関係を確定しない。識別子の伝搬や呼び出しの記録など、結びつけた根拠を示す。識別子が一致しても、全ての因果関係が分かるとは扱わない。

画面に表示する説明から、根拠となる記録をたどれるようにする。専門性に応じて説明の詳しさを変える場合も、同じ元の記録を参照する。

計測処理が実行のタイミングなどに影響する可能性がある。追加した計測処理を記録し、計測の有無による違いを比べられるようにする。

## 最初に確かめること

技術面では、出来事を誤って結びつけた箇所と、対応づけの取りこぼしを調べる。観測していない事実を確認済みとする誤りも調べ、別経路で確認した結果と照合する。

関係者が記録を見て、確認済みの内容と未確認事項を区別できるかを調べる。追加で必要な検証を選べるかも確認し、判断の内容と理由、かかった時間を記録する。参加者数と達成基準は、予備的なヒアリングと試行を踏まえて決める。

同じ観測情報から作ったテキスト説明と、既存のセッションリプレイや分散トレーシングを組み合わせた方法を比較対象にする。提供する情報と使える時間をそろえ、既存の方法でどこまで同じことができるかを確かめる。

初期版の完成条件は次のとおりとする。

- 正常時と3種類の異常条件を同じ記録形式で扱える。

- 根拠となる記録へたどれる。

- 未確認事項を表示できる。

- 記録に付けた問いから次の試行へ進める。

これらの達成だけでは、研究の新規性や医療現場での有効性を示したことにはならない。

## 実装前に次に決めること

最初の実行対象は、小さな再現用アプリとする。2026年10月2日の会話で合意した。既存のiOSとAWSのアプリへの適用は、再現用アプリで観測と評価の仕組みを確かめた後に検討する。再現用アプリの実行環境、操作や表示の方法、計測処理を入れる場所は、これから要件と設計で決める。

操作・データ・送信試行の識別子をどこで発行し、どう伝えるかを決める。保存処理のどの段階を記録するか、計測による影響をどう測るかも具体化する。OSやネットワークについては、初期版で実際に観測する範囲を明示する。

ヒアリングでは、相手が何を「届いた」「保存された」「使ってよい」と捉えるかを聞く。どの未確認事項が次の行動を妨げるかも確かめる。必要な支援と許容できるやり取りの回数は先に固定せず、ヒアリングの結果から検討する。

## 実装と比較に使う資料

記録方法と比較対象を検討するための一次資料として、次を参照する。この実験案の新規性を示す資料としては扱わない。

- [OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)：処理の関係や出来事を記録するためのモデル。

- [OpenTelemetry Context propagation](https://opentelemetry.io/docs/concepts/context-propagation/)：処理をまたいで文脈を伝える方法。

- [OpenTelemetry Sampling](https://opentelemetry.io/docs/concepts/sampling/)：取得・出力される記録の範囲を考えるための資料。

- [Sentry Session Replay](https://docs.sentry.io/product/session-replay/web/)と[Datadog Session Replay](https://www.datadoghq.com/product/session-replay/)：画面上の挙動と技術的な観測を共有する既存の方法。
