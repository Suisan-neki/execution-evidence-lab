# 目的、試作の仕様、未決定事項

目的と開発方針の更新日：2026年10月18日。各試作の記録は記載の日付時点。本人が指定した目的、実装側の設計案、未確認の業務条件を区別する。今回の方針更新だけで機能の実装完了とはしない。

## 本人が示した目的

本人が前に出したい価値は「技術者と非技術者で目線の高さを合わせる」「技術者が安心して世に出せる」。期待する動作と根拠・未確認事項を同じ記録で確認し、根拠に応じた安心感と誤った判断を分けて評価する。初期の確認者は医療機関の運用担当。持ち込まれたシステムの条件を具体化し、試行・改修・再検証へ進める。小さなアプリの完成だけを地方版未踏のゴールにしない。

2026-10-18、本人はAIなどで作った人が仕組みと挙動を確かめ、専門家とも同じ根拠から利用・改善を判断できる基盤という問題意識を示した。作成者と運用担当を同じ人が兼ねる場合も対象に含める。構想と実装案は[#157](https://github.com/Suisan-neki/execution-evidence-lab/issues/157)に記録した。

汎用版を先に公開する方針と11月の到達目標を維持し、医療情報版は共通基盤のモードとして並行開発する。[汎用版の計画](general-release-plan.md)に共通部分と作業順を記載した。

## 2026-10-18の実装案と未決定事項

- 事例・構成・条件・試行・根拠・履歴を共用する。医療向けには確認項目・説明・接続と観測のアダプターを追加する。
- 汎用／医療の設定と説明の詳しさを独立して扱う。表示を変えても判定と未確認事項を変えない。
- 設定と判定規則の版を保存する。条件を追加・変更した場合は適用範囲を確認し、過去の成功で新しい条件を埋めない。
- 次は共通設定と版の管理、参照アプリでの一往復、他の人が根拠へ戻れる確認資料を優先する。既存API・構成図・比較・出力を再利用する。
- 呼び出し番号表示は追加の参照アプリという案。OpenEMR・OHIF・MONAIへの適用と比較評価は維持する。
- 通信・保存などを制限する機能と、その結果を説明する機能を区別する。制限が効いた範囲は試験で確認する。

具体的な型・設定形式・医療向け確認項目は実装案。医療機関の採用済み要件とは扱わない。本人が示していない許容時間、利用者ごとの権限、実運用の接続先を実装側で決めない。医療モードの選択だけで安全性・適合性を確認済みにはしない。

## 理解とテストの二つの機能

2026-10-07に本人が指定した製品の中心は理解とテスト。理解では公開GitHubから構成・入口・処理と根拠コードをたどる。テストでは対象の処理を実行して期待する動作・失敗・未確認事項を確かめる。両機能は別々に使えて同じコードと結果へ対応づけられるようにする。

公開リポジトリから始めることは本人が選択済み。理解の最初の試作は宣言・参照先の簡易解析と作者の説明の表示。AIによる意味の説明と完全な処理解析は未実装。現在のテスト基盤の完成を製品全体の完成としない。詳細は[理解とテストの入口](repository-understanding.md)。

## 既存のテスト基盤で選んだ試作の仕様

| 項目 | 試作の扱い |
| --- | --- |
| データ | 架空の名前・年齢1件。空の名前と年齢151以上を拒否する既存判定を維持 |
| 操作 | CLIで条件を指定し、1回の送信を行う |
| 通信 | localhostのTCP、長さ付きJSON、最大64KiB |
| 保存 | 試行ごとの新規JSONファイル。書き込み・sync_all成功後に応答 |
| 表示 | 保存処理成功の応答を受信した場合だけDisplaySavedを記録 |
| 根拠 | 同じ試行・データ・送信試行に属するサーバーの保存記録を使う |
| 欠落・食い違い | 不足・矛盾をUnknownとし、独立した読み出しで埋めない |
| 再試行 | 新規ディレクトリを作り、previous_runで前の試行にリンク |
| 更新 | 条件・入力・コード・故障・実行環境の差を示す。変更された条件には旧規則を適用しない |
| 外部アプリ | プロセス記録を保存する。終了だけでは業務条件を判定しない |

| 共同レビュー | 同じ端末の画面で認識・出所・未回答と人の判断を保存。立場は自己申告 |
| 根拠の更新 | 条件版と宣言した依存先を照合し、古い根拠をUnknownにする。最新の不足を古い成功で埋めない |
| 比較資料 | 元の情報をそろえた4種類の資料と未記入の回答欄。通常のチェックリストの限定した参照実装も追加。利用者評価は未実施 |

理由と限界は[実装判断](implementation-decisions.md)に記載した。ファイル保存をDynamoDBや医療データベースの保証に読み替えない。

## 実システムで取得する必要がある情報

VitalSensingの固定版に対するローカルの索引更新ハンドラーは動かせる。模擬索引を使った結果だけでは、管理者が実データを閲覧できるとは言えない。

次に必要なのは、誰が何をどの時点までに閲覧できる必要があるか、失敗時に誰が対応するか、試験専用の保存先・認証・管理画面をどう固定するかという情報。条件の具体化は#68・#69・#94、環境の再現は#59・#80・#81で追う。許容時間や臨床上の条件を実装側で作らない。

## 固定版の外部実行で追加した試作（10月13日、PR #126）

Node.js/PythonのGit固定版を試行用にコピーし、明示した入力・引数と観測規則で動かす。画面から観測名・対象・設定を保存し、CLIで実行して同じ条件へ取り込む。結果から固定版・起動ファイル・観測の行を確認し、改修後の再試験へ進める。

観測は対象プログラムによる報告で、業務条件との対応は人が設定する。localはOSの隔離ではなく、Linuxのbubblewrapは起動不能時にlocalへ切り替えない。未回答の利用条件、実AWS・iOS・管理画面、独立した状態の確認、実参加者の理解・判断を実装側で補わない。[仕様](pinned-execution.md)。

## 10月14日の本人の優先順位

フロントエンドは簡素でよく、バックエンドの汎用版の完成を優先する。事例・条件・記録・判定・比較・再試験・バックアップと復元を、画面に依存しないAPIとCLIで使えるようにする。既存の理解機能は、公開GitHub読取と静的解析をAPIからも呼べるようにする。AI説明や完全な意味解析を不要と判断した意味にはしない。

言語を限定しない観測の接続には、外部から報告されたJSON形式を追加する。報告の出所・対象・識別子と条件を照合する仕様はCodexが選んだ試作で、医療機関の採用済み要件とは別。報告を、基盤が対象コードを実行・独立検証した証明にしない。

## 理解と試験の画面で追加した試作（10月14日）

本人の依頼で確認済みの目的：公開GitHubのURLから始め、理解・期待の確認・実際の故障を含む試行・結果の確認・修正後の再試験を一つの流れで行う。技術者と非技術者が、期待、実際の結果、まだ分からないことを同じ記録で確認する。終了コード0だけを成功にせず、人が確認していない内容を「合意済み」にしない。

Codexが選んだ試作の仕様（本人の採用前）：

- 実行できる対象はNode.jsとPython。依存関係のインストールは行わない。
- 判定の範囲は「受付」「書き込み」「後から読み出せた」。同じ範囲の観測が食い違うと判定できないにする。
- 確認は名前と役割の自己申告で、運用担当と開発者の両方が現在の条件の版で確認したときだけ「両者が確認済み」と表示する。
- 故障は、保存先の書き込み不可、保存先と同名のディレクトリ、基盤による読み出しの停止、ネットワークの遮断（bubblewrapの場合だけ）。

未決定の業務条件：誰が確認する必要があるか、確認者の本人確認の方法、許容する待ち時間、医療機関の稼働環境で使える実行方式、外部公開時の認証。詳細は[理解と試験の画面](understand-and-test.md)と[判断理由](implementation-decisions.md)。

## 実行の方法を広げる（#138）

本人が示した方針：OpenEMR、OHIF、MONAIのような実際の医療系OSSを試せるように、実行の方法を広げる。目標を実装の都合で小さくしない。順序は、固定した依存先と複数のプロセス（#137）、コンテナ（#139）、依存先の固定とビルド（#141）、ブラウザーでの操作（#140）。

#137では、Codexが次の試作の仕様を選んだ。本人はまだ採用していない。

- 依存先は、指定したリポジトリと固定コミットのファイルを読み込み先に置くだけで、インストールしない。
- 先に起動して待つプロセスを一つ持てる。ポートは基盤が選ぶ。
- 故障に、保存先のディレクトリを書き込み不可にする、待つプロセスを起動しない、を加えた。

未決定の業務条件：医療機関でDICOMの送受信を試すときの接続先と保存先、試験に使える画像、受信側の失敗を誰がどの時点で知る必要があるか。検証の記録は[pynetdicomでの検証](validation-dicom-2026-10-16.md)。

#139では、Codexが次の試作の仕様を選んだ。本人はまだ採用していない。

- コンテナはダイジェスト付きの公式イメージだけを起動する。
- 待ち受けは 127.0.0.1 だけ。試行の後にコンテナ・ネットワーク・ボリュームを消す。
- Dockerが使えないときは理由を示し、ほかの方式へ切り替えない。

未決定：Docker以外の実行基盤、公式イメージを使う場合の継続的な確認方法。検証の記録は[コンテナでの検証](validation-container-2026-10-16.md)。
