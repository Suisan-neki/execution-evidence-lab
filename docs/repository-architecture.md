# リポジトリからシステム構成を理解する

公開GitHubの固定コミットからREADMEとコードを読み、AIがそのシステム固有の役割と情報の流れを整理する。GitDiagramの構成把握と構造化した図の生成を踏襲する。従来の静的な種類の分類を、利用者向けの構成図の生成には使わない。

## 開発者・運営者がAPIキーを設定する

APIキーはこのサービスの開発者・運営者がサーバーへ設定する。利用者はキー、モデル名、接続先を入力しない。利用者向けの画面とAPIには接続設定の作成・変更機能を設けない。

最初に、開発者の端末で次を実行する。

```bash
cargo run -- ai init
```

`data/app/ai.json`が所有者だけが読み書きできる権限（0600）で作られる。既存のファイルは上書きしない。エディタでこのファイルを開き、`api_key`に作成したキー、`model`に利用するモデル名を記入する。`base_url`はOpenAI互換APIの接続先で、ひな形には `https://api.openai.com/v1` を指定している。モデルはChat CompletionsとJSON応答に対応するものを契約先から選ぶ。キーや利用枠の有効性は、実際の接続で確認する。

```bash
cargo run -- ai test
cargo run
```

`ai test`は設定したモデルへ短い問い合わせを送り、応答の有無を端末に表示する。APIキーや応答の生データは表示しない。接続確認は数十秒以内で終わる。構成図の生成は抜粋を送るため数分かかることがある。生成の待機上限は300秒。上限に達した場合は接続失敗とは別に表示する。接続確認後にサーバーを起動すると、利用者は立場を選び、GitHubのURLを入力して構成図を作れる。

`data/`はGitの管理対象外。キーをソースやチャットへ貼る必要はない。設定はサーバー起動時に読み、変更後は再起動する。保存先を変える場合は `ai init --data-dir DIR`、`ai test --data-dir DIR`、`app DIR` で同じディレクトリを指定する。

配備先の運営者は、既存の `EEL_AI_BASE_URL`、`EEL_AI_MODEL`、`EEL_AI_API_KEY_FILE` による起動時設定も使える。三つをすべて指定した場合はファイルより優先し、一部だけの指定は起動エラーにする。ファイルがなく未設定のときは保存済みの図を開けるが、新しい図の生成やAIへの質問は行わない。

AIへの通信はRustサーバーが担当する。生成と質問にNode.jsは不要。対象がNode.js製の場合の実行には、別途Node.jsが必要。接続や生成の失敗時は理由を表示し、別の図や固定文で補わない。

## 画面で行うこと

リポジトリURLを入力して「構成図を作成する」を押す。READMEとコードの抜粋を設定したAI接続先へ送る。対象コードは起動しない。AIは目的、主な情報の流れ、利用者、画面、業務上の処理、保存先、外部連携を同じ構成モデルへ整理する。

図では、そのシステム固有の役割名と短い説明を表示する。実際のサブシステムのまとまりを枠で表し、役割の種類の分類を配備境界として描かない。非技術者と技術者は同じ要素・接続・配置を参照する。技術者には技術名と実装の詳しい説明を追加する。図全体は表示領域に収め、拡大とスクロールで詳細を読める。

箱や線を選ぶと説明と根拠を確認できる。不安や疑問を入力して「AIと疑問を整理する」を押すと、その図の選んだ部分と関連するコード・設定を基に説明を得る。疑問の整理は一回ごとの質問で、過去の対話を自動で引き継ぐ機能はまだない。AI回答だけでは発言、期待、試験結果を保存しない。記録する内容を自分で確認し、疑問と検証したい動作を保存する。

検証設定と結果は既存の詳細画面で扱う。構成図へ戻ると、疑問を残した図の版と要素・接続を開く。AIが作った構成図を、実行済み・安全確認済みの証拠にしない。

## 読取・生成・検査・保存

`src/system_diagram.rs`が生成と保存、`context.rs`が行番号を保った抜粋、`model.rs`が出力の検査と既存の構成モデルへの変換を担当する。AIの指示は `prompt.txt`、参照元とMIT Licenseは `third_party/gitdiagram` に記載する。

初回の読取に加えて、構成に関係する候補を最大48ファイル補う。AIへ渡す文脈は160KiB以内、ファイル一覧は24KiB以内、本文は最大64ファイル、README等の説明資料は最大6件とする。長いコードの冒頭・中ほど・末尾から分散して抜粋し、実際に渡した行番号を保持する。モデルへ渡さなかった行を根拠として認めない。未読であることから機能が存在しないとは判断しない。

AIは最大34要素、48接続、10グループのJSONを返す。RustがIDの形式・重複、親グループ、接続の両端、実装のパス、説明の上限、根拠の種類と渡した行範囲を検査する。不正な出力には検査結果を返して一度だけ修正を求める。修正後も不正なら図を更新しない。

参照の照合は行が存在することの確認であり、AIの説明や接続方向の正しさの証明ではない。コード、作者の説明、直接の記述が不足する推定を表示で区別する。推定と設定・起動の依存は点線にする。描画する文字列はDOMのテキストとして扱い、モデルのHTMLやJavaScriptを実行しない。ELKはブラウザ内で配置し、外部作図サービスやCDNへモデルを送らない。

成功した図は内容と文脈から求めた版ごとに保存する。通常の再表示は保存した図を使い、AIへ再度問い合わせない。AI設定がない状態でも保存済みの図を開ける。「構成図を作り直す」を明示したときに再生成する。再生成に失敗しても以前の成功した図を残す。保存先全体の保全が必要で、事例だけのバックアップには図や運営者のAI接続設定を含まない。

## API

| 操作 | 用途 |
| --- | --- |
| `GET /api/v1/ai` | 設定の有無・接続先ホスト・モデル名。キーは返さない |
| `POST /api/v1/system-diagram` | `repository`・`commit`から保存済みの図を開くか生成する。`revision`で過去の図、`refresh:true`で再生成 |
| `POST /api/v1/system-diagram/question` | 図の版と部分を指定し、根拠に対応した疑問を整理する |

いずれも既存のlocalhost APIのトークンと送信元の確認を使う。ブラウザからの設定変更・接続確認APIは提供しない。

## 確認範囲

合成のモデル応答で、参照外の行・重複ID・存在しないパス・不正な接続の拒否、修正後の生成、保存と再表示、再生成失敗での保持、キーの非公開、開発者のCLIでの接続確認、立場別の同じ図、疑問と検証の往復を確認する。これを実モデルの図の品質や利用者の理解評価とは扱わない。

この環境には実モデルのAPIキーがないため、実モデルでの生成品質、対象リポジトリの説明の網羅性、生成時間・費用、他者の理解は未確認。GitDiagramの生成方針とプロンプトを参考にした実装で、同等の品質は未確認。入力するモデルはChat CompletionsとJSON応答に対応する必要がある。詳細は[生成方式の変更と確認記録](validation-ai-architecture-2026-10-21.md)。
