# execution-evidence-lab

小さな再現用アプリを実際に動かし、利用者の操作や表示と、通信・受信・保存に関する観測結果を結びつける研究用リポジトリ。

## 目的

関係者が同じ実行記録を見ながら、確認できたこと、まだ確認できないこと、次に試す条件を説明できるようにする。

実験では、アプリの操作・表示と下の層で観測した出来事を対応づける。対応づけに使った根拠と、観測できなかった範囲も残す。記録方法の妥当性と研究の新規性は、これから実験と既存研究・ツールの調査で確かめる。

## 最初の実験

最初の実行対象は、小さな再現用アプリとする。架空のテスト用データ1件を送る流れについて、まず正常時の観測と、実際に保存されたデータの照合を確かめる。

その後、次の3条件を同じ記録形式で扱う。

- 送信要求がサーバーの受信処理に届く前に、通信を切る。
- サーバーで受信した後、DBへの保存を確定する前に失敗させる。
- 処理は正常に動かし、保存に関する観測記録の一部を取得させない。

具体的な故障の起こし方と取得する記録は、Codexが設計案を示し、本人がPRをレビューして決める。

## 現在の段階

正常時の1件送信に向けて要件と設計を整理する段階。src/main.rsには入力検証のコードがあるが、実装言語にはRustを使う方針がある。実行環境、画面や操作の方法、使用するライブラリ、データの項目、成功表示の意味は未決定。

初期コミットには、目的、実験条件、要件を記入する欄、レビュー手順が入っている。再現用アプリ全体の実装と実験は未完了。コードがあることと、仕様の採用・実験による確認は区別する。

## 読む順番

1. [初期実験仕様](docs/first-experiment.md)で、合意済みの範囲と設計案を確認する。
2. [最初の要件](docs/requirements.md)で、合意済みの内容と未決定事項を確認する。
3. [開発ロードマップ](docs/roadmap.md)で、目的、現在地、実装順序、各PRで判断することを確認する。
4. [協働手順](AGENTS.md)に沿って、Codexが小さな変更を作り、本人がPRをレビューする。

2026年10月5日から、Codexが要件・設計の案、コード、必要なテストを作り、1つの変更目的ごとにPRを提出する。本人はコードを読んで採用・修正・却下を判断し、自分で修正することもできる。通常は1件ずつレビューし、前のPRに依存する実装は、そのPRのマージ後に進める。Codexは本人の明示的な指示なしにマージしない。

## Cursorで始める

リポジトリを手元に取得し、execution-evidence-labフォルダーをCursorで開く。

```bash
git clone https://github.com/Suisan-neki/execution-evidence-lab.git
cd execution-evidence-lab
```

このリポジトリのCodexセッションでは、次のように依頼できる。

> AGENTS.md、docs/first-experiment.md、docs/roadmap.md、docs/requirements.mdと現在のコードを読んで。Codexが小さな変更ごとにPRを出し、私がコードを読んで判断・修正する進め方で進めて。まず現在の入力検証を確認し、最初のPRの範囲を示して。期待する動作が未決定なら必要な点を確認し、合意した範囲を実装・検証してPRを1件作って。

Rustの環境を用意する手順は、作業するPCのOSと既存の設定を確認してから決める。

## 調査と実験の記録

既存のトレーシングやセッションリプレイでどこまで同じことができるか、実装と並行して調べる。実験では故障条件、基盤が観測した記録、別経路で確認した実際の状態を区別して保管する。

1回の試行結果や学習レビューの通過から、製品全体の運用の安全性を判断しない。何を確認したかと、未検証の範囲を説明できることを重視する。
